# locus megaplan: maximize the judging score

## Score sheet

Each criterion is worth 10 points, 30 in total.

| Criterion | What the judges ask | What we must show them |
|---|---|---|
| Impact | How useful is the tool to scientists? Does it solve a real pain point? | A real researcher's pain, in their own words, and a measured before-and-after |
| Technical execution | Does the tool work? Is it usable? Does it solve the problem it claims to solve? | A live run that does not fail, numbers checked against ground truth, and no invented facts |
| Presentation | Can non-experts understand the problem, why it matters and the solution? | One story, one demo question and one result, with no jargon |

## What the judges' affiliations suggest

These notes use affiliations only. Check each person's public profile before the pitch.

- **Maxim Tsenkov, PDBe (EMBL-EBI).** EMBL-EBI also runs PRIDE, Europe PMC, ArrayExpress and BioStudies. Expect questions about metadata quality, provenance and the correct use of repository APIs. Show accessions, counts traced to sample records, and the API sources.

## Positioning

> The data to answer your question often already exists, buried among 340,000 public studies. locus finds it, shows you why it fits, and proves it with the authors' own records.

We make three claims, and each one maps to a pain point in `product.md`:

1. **It finds the data.** This removes the manual hunt through Google, then Ctrl-F, then GEO.
2. **It understands the biology.** It knows which methods can answer the question, and it does not confuse TIS-seq with Ribo-seq.
3. **It proves the fit.** It shows counted samples, the authors' QC, and methods text that shows how the samples are matched, all cited.

## Workstreams

### A. Make it correct and measurable (Technical execution, the foundation)

1. Fix the drift between the backend and frontend schemas. The `assays`/`repositories` rename broke `/search` today. Add one smoke test that runs `/search` end to end against a fixed question.
2. **Build a ground-truth set with the team researcher.** Label 20 to 30 datasets across two questions: the demo question about translation and the fibrosis question. Record each dataset's assay type, whether the samples are matched, the case and control counts, and whether the dataset is relevant.
3. Write an eval script that reports these four numbers:
   - Assay-type accuracy.
   - Case and control counts that exactly match the records.
   - Precision of "usable as is".
   - Recall of the datasets the researcher knows.
4. Add an "How we check our work" page that shows these numbers and the known limits, including the counts, which count samples and not patients. Honest numbers count for more with these judges than high numbers.
5. Cache the demo searches and their corpora so the live demo never waits 60 seconds or fails.

### B. Evidence assistant: chat over the papers (Impact and Technical execution)

1. **Corpus.** For each result, fetch the open-access full text from Europe PMC. Split the methods and results sections into paragraphs and index them with FTS5 in `store.py`. Start the fetch as soon as the results arrive.
2. **`POST /chat`.** The endpoint streams NDJSON. It uses Claude (`claude-opus-5-5`) with three tools:
   - `search_passages` finds paragraphs across the papers.
   - `get_dataset` returns counted facts and sample groups.
   - `compare` sets datasets side by side.

   Passages go in as `document` blocks of custom content with `citations: {enabled: true}`. Citations stream back as `citations_delta` events with a `content_block_location`, and the document blocks are cached.
3. **Rules.**
   - Every claim must have a citation.
   - When the paper does not say something, the answer is "not stated in the methods".
   - The interface shows how much full text is available, for example "Methods available for 21 of 32 papers".
4. **Interface.**
   - Use AI Elements components (Conversation, Message, PromptInput, InlineCitation, Suggestion) in the locus style.
   - The chat sits in a panel beside the results table, and each table row has an "Ask about this" action.
   - A citation opens its paragraph with the quoted span highlighted.
5. **Trust matrix.** Ask "Which datasets have truly matched RNA-seq and Ribo-seq?" and get back a table. Its columns are assay, where the samples were split, replicates and author QC. Every cell is either cited or marked "not stated".

### C. Biology-aware search (Impact: pain point 2)

1. **Assay identity from the methods.** Classify each dataset from the methods paragraphs, not from the repository library field. For example, harringtonine or lactimidomycin means TIS-seq, cycloheximide-arrested footprints mean Ribo-seq, and Ribo-STAMP uses an APOBEC fusion. Show the assay with its citation, and warn when the repository label and the methods disagree. This answers the researcher's example of the agent that "confused TIS-seq for riboseq".
2. **Method-fit notes.** The plan already has `method_notes`. Show them before the results as "What can answer this". For an isoform question, it should say that Ribo-seq reads rarely span exon junctions and suggest Ribo-STAMP or long-read methods. The researcher asked for exactly this.

### D. Breadth: more omics types (Impact)

Add one repository from EMBL-EBI, chosen by what the demo needs. Options:

- **ArrayExpress or BioStudies.** These are relevant to the PDBe judge.
- **MetaboLights.** This adds metabolomics, which the researcher listed.
- **SRA run info, through the existing E-utilities.** This is used for FASTQ handoff (workstream E).

Add only one before the event. List the others on the roadmap slide.

### E. Handoff to analysis (Impact: pain point 3; a bridge, not a pipeline)

1. Keep the download plan. Add a run-level manifest built from SRA run info (accession, run, layout, read length).
2. **Export a samplesheet for nf-core or riboseq-agent** for the selected rows. This is the researcher's next step, and it costs one CSV export. Do not run the pipelines.
3. Add a "Ready to process" status for each dataset: raw reads available, processed matrix available, or controlled access.

### F. Agent interface (Technical execution, as a differentiator)

The MCP server already exists, with `search_datasets` and `geo_sample_groups`. Add `ask_papers` once workstream B is done. In the pitch, show 20 seconds of an AI scientist agent calling locus as a tool. It costs little and fits an AI-literate panel.

### G. Presentation (worth 10 points on its own)

1. **One demo question, from the researcher's own field.** Use matched RNA-seq and Ribo-seq before and after mTOR inhibition. First check that the search returns good results for it. Fall back to the fibrosis question if it does not.
2. **A timed before-and-after.** The team researcher does one fresh question manually, with a stopwatch. Then the same question runs in locus. Show both times.
3. **Pitch structure (about 3 minutes).**
   1. The problem as a human story (20 s). The data is buried, and finding it takes days of detective work.
   2. A quote from the researcher about the agent that confused TIS-seq with Ribo-seq (10 s).
   3. Live demo (90 s): ask the question, show the results table, run the trust-matrix question, click one citation through to the paper.
   4. Proof (30 s): the eval numbers and the timed comparison.
   5. Roadmap (20 s): processing handoff and monitoring for new data.
   6. A one-line close.
4. **Fallbacks.** Record the demo on video, cache every query, and keep screenshots in the deck.
5. **Landing page.** Keep it to one page: the problem, the three claims, the numbers and a "Try it" link. Make it from the brand board.
6. **Make it reachable for the judges.** Use a public tunnel or a deployed web front end with the API on one machine. The 776 MB index makes a full deploy heavy, so decide on day 1.

## Cut list (do not build before judging)

- Monitoring for newly published datasets. It goes on the roadmap slide only.
- Raw FASTQ processing, ΔTE calculation and running pipelines.
- A vector database. FTS5 is enough for about 30 papers.
- Accounts, saved sessions and chat history across searches.
- More than one new repository.

## Risks

| Risk | Mitigation |
|---|---|
| The demo question returns weak results | Test it on day 1, and keep the fibrosis question as the fallback |
| Many papers lack open-access full text | Show the coverage figure. The assistant answers only from what it has. |
| The live API is slow or fails | Use cached queries and the recorded video |
| The two sessions edit the same files | Assign file ownership per track, for example `results.tsx` to one person only |
| Turbopack serves stale CSS | Stop the dev server, delete `web/.next/dev/cache`, then start it again |
